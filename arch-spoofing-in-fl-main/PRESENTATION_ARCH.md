**Scope.** The **model** axis only: clients running different architectures, the server
grouping them by the architecture they **declare**, and an attacker lying about it. Two
sources of evidence, kept clearly apart throughout — a **live re-run** in the current Torch
codebase (MNIST, 12 clients, 2 architectures, 6 rounds of 2 epochs, 1 attacker, 3 seeds),
and an **archived corpus** from August (1512 rows, 2 datasets, 5 architectures, 3 seeds).

## The one-sentence version

> An attacker who is *willing to train the architecture it declares* is placed in the
> victim's cluster **every round**, survives the shape check **by construction**, and is
> flagged by behavioural fingerprinting **less often than an innocent client**. The attack
> is limited by **capability**, not by knowledge.

Four results are worth your time above the others. **The inversion**: this channel and the
data channel fail for *opposite* reasons, which is what makes reporting both worth more
than reporting either twice. **The free defence has a ceiling**: the weight-shape check
stops the naive spoofer 100% of the time and the adaptive one 0% of the time, and nothing
in between. **The negative result**: fingerprinting scores 0.250 against a 0.343
false-alarm rate, so the defence direction we hoped for does not work. **The replicated
correction**: robust aggregation contains the damage but not the intrusion — the same
finding as Part A, now holding independently on a second channel.

## 0. Method, and the five questions I expect first

The same five questions as the Part A presentation, answered up front rather than in an
appendix, because they decide whether anything after them is worth hearing.

### 0.1 How is the clustering actually performed?

**It is not inferred. It is read off a declared field**, and that is the entire point.

`clustering.ArchitectureClusterer` groups clients by `metadata['arch']` — a string the
client sends. The cluster id *is* the architecture name. The server then keeps **one
global model per architecture** and runs FedAvg inside each.

This is a genuine difference from Part A, where the server ran a cosine bipartition over
update vectors and had to *recover* the grouping. Here there is nothing to recover, so:

- `needs_delta = False`. The clusterer never looks at the weights.
- **Cross-architecture cosine is never computed, and must not be.** Different
  architectures have different parameter counts, so their update vectors are not
  comparable. `TorchFederatedServer.fit` records separation and Adjusted Rand Index (ARI)
  as `None` in architecture mode rather than computing a meaningless number.
- There is no "do the groups exist?" question. They exist by construction.

**Why a server would ever do this.** Because it has to. If a hospital runs a small dense
network on a laptop and another runs a convolutional network on a GPU, their weights
cannot be averaged together — the tensors do not line up. Grouping by declared
architecture is not naive, it is the *minimum* a heterogeneous federation must do to
function at all. The vulnerability is that the field is **unverified**.

### 0.2 How does the imitation work, and how do you know it worked?

There are **two tiers**, and the difference between them is the whole attack.

| tier | what it **declares** | what it **trains** | what happens |
|---|---|---|---|
| **naive** | `dnn_flat` | `mlp_flat`, its own | 110,156 numbers arrive where 578,894 are expected — **rejected** |
| **adaptive** | `dnn_flat` | **`dnn_flat`, the one it declared** | shapes match — **accepted** |

The adaptive tier is implemented by `attacks.ArchSpoof(adaptive=True)`, and the mechanism
is one hook: `training_arch(client_id, true_arch)` returns the **declared** architecture,
so the client warm-starts from the victim cluster's model and trains *that* network on its
own data. Its submission genuinely **is** a `dnn_flat` update. There is no forgery to
detect because nothing was forged — the lie was **made true**.

That is the same move as Part A's adaptive distribution spoof, which changed what the
model behaves like so it matched what was declared. Same principle, different axis.

**How I know it worked**, and it is measured three ways, not asserted:

1. **Infiltration** — the fraction of rounds the attacker sat in the target
   architecture's cluster. **1.000** for the adaptive spoof.
2. **`shape_rejected_rounds`** — how many of the 6 rounds the server threw the update
   out. **0** for adaptive, **6** for naive.
3. **A measured control** — the same client, same seed, doing nothing. **0.000**
   infiltration. Without this the 1.000 means nothing.

### 0.3 Are the malicious clients really training on their own data?

**Yes.** This is the question I would ask too, because if the attacker were handed the
victim's data the result would be circular.

The attacker's data is untouched. `ArchSpoof` implements `training_arch` and `apply`; it
does **not** implement `training_data`, so the client's own Dirichlet shard is what goes
into the optimiser. What the attack changes is only:

- **which network** those samples are trained on (the declared one), and
- **which cluster's model** it warm-starts from (the victim's).

So the attacker contributes a genuinely-trained `dnn_flat` update, computed on its own
local data, into a cluster it does not belong to. That is exactly the threat model: a
participant with real data and real compute, lying about one metadata field.

### 0.5 How was the attack evaluated?

**Against a measured control in every case, never against an assumption.**

| metric | what it answers | control it is scored against |
|---|---|---|
| **infiltration** | did it get in? | the same client, not attacking |
| **`shape_rejected_rounds`** | did the free defence stop it? | 0 for an honest client |
| **victim-cluster accuracy** | did it do damage? | the same run with no attacker |
| **fingerprint detection** | can a defender see it? | the **honest false-alarm rate**, out-of-sample |

Two evaluation choices carry real weight:

**Victim-cluster accuracy, not global accuracy.** Global accuracy averages the victim's
loss against clusters the attacker never touched, which dilutes the effect toward zero.

**Fingerprint detection is leave-one-seed-out.** Train on honest clients from every seed
but one, score the held-out seed. An earlier version fitted and scored the same rows and
got a false-alarm rate of **0.000** — a random forest has no training error, so that was
an artefact, and it made a 27% detection rate look like signal. Fixing it **changed the
conclusion**.

## 1. Why this is not "Part C"

The project attacks **one trust boundary through two channels**. They are different axes,
not a sequence.

| channel | server groups on | what differs between groups | the lie |
|---|---|---|---|
| **architecture** | `metadata['arch']` | the **model** each client runs | declare a model you do not run |
| **data distribution** | `metadata['label_hist']` | the **data** each client holds | imitate a distribution you do not have |

`RESULTS.md` Parts A and B are two kinds of **data** heterogeneity — distribution shift
and concept shift — tested separately so they can replicate one another. This document is
the **model** axis. It also came **first**: the repository is named `arch-spoofing-in-fl`
for it.

**Please use the channel vocabulary, not a part letter.** It is accurate, it is the
project's own original framing, and it makes the report's structure obvious.

## 2. Architectures do leave a behavioural signature

*Code: `cfl-architecture.ipynb` **Cell 17** (Part 4).*

*Source: archived corpus, honest clients only, no attack, no payload.*

Before asking whether fingerprinting defeats a spoofer, establish whether it can tell
architectures apart when **nobody is lying**.

![Feature distributions](docs/figures/s1_feature_distributions.png)

A meta-classifier predicting the architecture from probe behaviour alone:

| dataset | clients | architectures | accuracy | majority baseline | lift |
|---|---|---|---|---|---|
| IDS | 108 | 3 | **0.806** | 0.333 | **+0.472** |
| MNIST | 108 | 4 | **0.509** | 0.333 | +0.176 |

![Confusion](docs/figures/s1_confusion.png)

The most informative feature by a wide margin is `pred_dist_gini` at **0.1861** — the
concentration of the model's predicted-class distribution. Architectures differ most in
**how peaked their outputs are**, not in how accurate they are.

> **Verdict.** Better for the **server**, and it is the precondition everything after it
> needs. If architectures were behaviourally identical, no fingerprint could exist and no
> later number would mean anything. Strong on IDS, weak on MNIST — worth remembering when
> the detection numbers arrive.

## 3. The trap: parameter count makes this trivial and meaningless

*Code: `cfl-architecture.ipynb` **Cell 19** (Part 5).*

Any feature derived from parameter or layer count wins completely and tells you nothing:

| feature set | IDS | MNIST |
|---|---|---|
| shape-agnostic (the headline) | 0.806 | 0.509 |
| plus shape-dependent | **1.000** | **1.000** |
| **`n_params` alone** | **1.000** | **1.000** |

![Shape leak](docs/figures/s1_shape_leak.png)

**Parameter count alone identifies the architecture perfectly, and tells the server
nothing it did not already know.** The declared architecture already implies the shape,
and an adaptive spoofer's shape matches *by construction*. A fingerprint built on shape is
not a defence — it is a restatement of the declaration.

This is the architecture channel's version of Part A's full-vector trap: an apparently
perfect signal that is useless for the question actually being asked. **The headline
classifier therefore uses shape-agnostic features only**, and every detection number below
depends on that choice.

> **Verdict.** Neutral as a number, **essential as a method decision.** Reporting the
> 1.000 as a defence would have been the single easiest way to make this study wrong.

## 4. Both tiers get placed. Only one survives.

*Code: `cfl-architecture.ipynb` **Cell 10** (Part 3). The mechanism itself is **Cell 8** (Part 2).*

*Source: the live re-run. Driver `sweeps_arch.sweep_tiers()`, data in
[`experiments/m1_spoof_tiers/`](experiments/m1_spoof_tiers/).*

![Spoof tiers](docs/figures/arch_1_tiers.png)

| condition | infiltration | rounds rejected | victim accuracy | control |
|---|---|---|---|---|
| control, no spoof | **0.000** | 0 | 0.9157 | — |
| naive spoof | **1.000** | **6 of 6** | **0.9157** | 0.9157 |
| adaptive spoof | **1.000** | **0 of 6** | 0.9250 | 0.9157 |

**Placement is not the hard part, and that is the first finding.** Both tiers infiltrate
every round, because placement depends *only* on the declared string. The clusterer cannot
tell them apart and never could — it never looks at the weights.

**The free defence is all-or-nothing.** The naive spoofer is rejected in **6 rounds out of
6**, every seed. And the proof that rejection is *total* rather than merely frequent is
this: its victim-cluster accuracy equals the control's **to six decimal places on every
individual seed** — 0.9330, 0.8975, 0.9165. Not on average. Exactly. A client whose every
update is discarded has left no trace at all.

**The adaptive spoofer is never rejected.** 0 of 6, every seed, because its update
genuinely is the architecture it claims. There is no mismatch to find.

**And with no payload attached, it does no damage — it very slightly helps** (+0.0093).
That is the honest reading and I want to state it plainly rather than bury it: an
infiltrator that trains properly on real data is, in accuracy terms, just an extra
contributor with more capacity. **Placement is the precondition for harm, not harm
itself.** What harm looks like is section 6.

> **Verdict.** **Better for the attack, worse for the server, and it narrows the defence
> question usefully.** Shape validation is free and it works perfectly — against the tier
> that was never the threat. Against an attacker willing to train the model it declares it
> contributes exactly nothing. Everything the server might do about the adaptive tier has
> to come from somewhere else.

## 5. Fingerprinting does not catch the adaptive spoof

*Code: `cfl-architecture.ipynb` **Cell 21** (Part 6).*

*Source: archived corpus. This is the strongest negative result in the project.*

![Detection by mechanism](docs/figures/s2_detection_by_mechanism.png)

Three detection mechanisms, **reported separately and never pooled**, because conflating
them is how a defence gets credited with work it did not do:

| condition | payload | shape check | non-finite | fingerprint |
|---|---|---|---|---|
| naive spoof | none | **1.000** | 0.000 | 0.972 |
| naive spoof | boost | **1.000** | 0.722 | 0.250 |
| naive spoof | sign flip | **1.000** | 1.000 | n/a |
| adaptive spoof | none | **0.000** | 0.000 | **0.250** |
| adaptive spoof | boost | **0.000** | 0.000 | 0.472 |
| adaptive spoof | sign flip | **0.000** | 0.000 | 0.917 |

**Honest false-alarm rate, out-of-sample: 0.343.**

**The adaptive spoofer with no payload is flagged less often than an innocent client** —
0.250 against 0.343. A detection rate at or below the false-alarm rate is the classifier's
**error rate, not a detection**.

**Where detection does happen, it is finding the payload, not the spoof.** Sign-flipping
scores 0.917, but sign-flipping a BatchNorm network produces negative variances and
therefore non-finite output, which any verifier catches trivially. The corpus records
`nonfinite_rate` separately precisely so this cannot be mistaken for fingerprinting, and
the architecture pool deliberately includes `mlp_plain`, a BatchNorm-free network, as the
control for it.

> **Verdict.** **Better for the attack, worse for the server, and it closes a defence
> direction we had hoped would open.** An attacker that infiltrates and delivers nothing —
> or delivers a boost that keeps the update's direction honest — passes every check the
> server has. Behavioural fingerprinting cannot separate a well-executed architecture
> spoof from an honest client.

## 6. What the spoof costs the victim, once it carries a payload

*Code: `cfl-architecture.ipynb` **Cell 23** (Part 7).*

*Source: archived corpus, run end to end through the server, pooled over seeds with
bootstrap intervals.*

![Impact versus alpha](docs/figures/s4_impact_vs_alpha.png)

| Dirichlet alpha | baseline | under attack | degradation | relative drop |
|---|---|---|---|---|
| 0.1 | 0.4917 | 0.1692 | 0.3225 [0.248, 0.470] | **65%** |
| 0.5 | 0.8342 | 0.1667 | 0.6675 [0.485, 0.762] | **79%** |
| 10.0 | 0.9950 | 0.2575 | 0.7375 [0.735, 0.740] | **74%** |

Effect sizes are large everywhere: Cohen's *d* of **2.52**, **4.22**, and one so large the
standard deviation collapses.

![Effect sizes](docs/figures/s5_forest.png)

**And the effect is the treatment, not the seed.** Decomposing the variance in
victim-cluster accuracy:

| factor | share of variance |
|---|---|
| **condition** | **0.759** |
| alpha | 0.135 |
| **seed** | 0.003 |
| residual | 0.103 |

![Variance decomposition](docs/figures/s5_variance.png)

Seed accounts for **0.3%**. Condition accounts for **76%**. This is not seed noise.

**Quote the degradations, not the absolute accuracies.** The clients here hold
Dirichlet-partitioned data, which does not affect *who is in which cluster* — clusters are
declared — but does put the absolute numbers on a partition the project has since moved
away from. The relative drops are the transferable result.

> **Verdict.** **Worse for the clients in the victim cluster, and severely.** A 65–79%
> relative accuracy loss is not degradation, it is destruction of the cluster's model.
> Note the pairing with section 4: placement alone was harmless, and placement plus a
> payload is catastrophic. **The declared-metadata lie is the delivery mechanism; the
> payload is the weapon.**

## 7. The inversion: the two channels fail for opposite reasons

*Code: `cfl-architecture.ipynb` **Cell 32** (Part 9).*

This is the sharpest thing in the study, and it is why reporting both channels is worth
more than reporting either one twice.

**Part A's binding limitation is knowledge.** The attacker cannot work out the target
group's label distribution — it is continuous, high-dimensional, and the broadcast model
leaks it at a couple of percentage points per class. Measured, the `inferred` channel
scored 0.0844 against `blind` 0.0887 with overlapping intervals: **not distinguishable**.
An attacker *told* the answer imitates perfectly; one that must *deduce* it cannot.

**Architecture has none of those properties.**

| | data distribution | architecture |
|---|---|---|
| the thing to be guessed | a continuous vector over classes | **one name from a short list** |
| size of the space | effectively unbounded | **5 here, 7 in the live registry** |
| is it public? | no, it is the victim's private case mix | **yes, architectures are published** |
| readable from what the server sends? | barely, a two-point leak | **yes, parameter shapes give it away** |
| **binding constraint** | **knowledge** | **capability** |

Section 3's shape-leak table is the evidence for that fourth row: `n_params` alone
identifies the architecture at **1.000**. **The same fact that makes shape-based
fingerprinting useless as a defence makes architecture trivially knowable to an attacker.**
One measurement, cutting both ways.

> **Verdict.** **Better for the attack than the data channel is.** Distribution spoofing
> is bounded by knowledge and free in capability. Architecture spoofing is bounded by
> capability and free in knowledge — and "capability" here means *being able to train a
> second small network*, which for any realistic attacker barely binds at all.

## 8. Does robust aggregation help?

*Code: `cfl-architecture.ipynb` **Cell 25** (Part 8); the two failures below are **Cell 30**.*

*Source: the live re-run. Driver `sweeps_arch.sweep_agg()`, data in
[`experiments/m3_aggregators/`](experiments/m3_aggregators/). Six rules × 2 conditions ×
3 seeds = 36 cells.*

**A payload is required for this question to mean anything.** Section 4 showed placement
alone does no damage — the adaptive spoofer even helps slightly — so with nothing to
contain, all six rules would tie trivially. The attacker here carries a **10× weight
boost** (model replacement, Bagdasaryan et al.), composed onto the spoof.

![Aggregation](docs/figures/arch_3_aggregation.png)

| aggregator | placement | control | victim, attacked | victim, control | accuracy lost |
|---|---|---|---|---|---|
| **fedavg** | 1.000 | 0.000 | 0.7350 | 0.9157 | **+0.1807** |
| krum | 1.000 | 0.000 | 0.7968 | 0.7938 | −0.0030 |
| trimmed | 1.000 | 0.000 | 0.9303 | 0.9257 | −0.0047 |
| median | 1.000 | 0.000 | 0.9320 | 0.9267 | −0.0053 |
| multikrum | 1.000 | 0.000 | 0.9157 | 0.9093 | −0.0063 |
| bulyan | 1.000 | 0.000 | 0.9207 | 0.9093 | −0.0113 |

**Placement is 1.000 under every rule, with a clean 0.000 control.** No aggregation rule
stops the intrusion, and none could: **placement is decided before aggregation runs**. The
clusterer has already seated the attacker by the time any rule gets a vote.

**Plain averaging loses 18.1 percentage points**, and consistently — +0.1910, +0.1365,
+0.2145 across the three seeds, never near zero.

**All five robust rules lose essentially nothing**, between −0.0030 and −0.0113, with
per-seed values straddling zero in both directions. That is noise, not containment failure.

**This replicates Part A's correction on a different channel**, which is the strongest
form the claim has taken: the literature-review paragraph saying Byzantine-robust
aggregation defends against this class of attack is **wrong about intrusion and right
about damage**, and that now holds in the data channel and the model channel independently.

**One caveat the table makes visible.** Krum's *control* accuracy is 0.7938 against
FedAvg's 0.9157 — it pays **12.2 points of clean accuracy** for its robustness, because it
selects a single update and discards the rest. Its damage figure of −0.0030 is real, but
"robust aggregation is free" is not the lesson. Median and trimmed mean are the rules that
contain the damage *and* keep the accuracy.

> **Verdict.** **Better for the server on damage, and no help at all on membership.**
> A defender who deploys median or trimmed mean neutralises this payload for roughly
> nothing. But the attacker is still **inside the victim's cluster every round**, still
> counted in its statistics, and free to switch to a payload that survives coordinate-wise
> filtering. **Containment is not eviction.**

### A methodological note I would rather volunteer

The first version of this experiment was wrong **twice**, and both failures produced
plausible-looking numbers rather than errors.

**First, the payload never fired.** `ArchSpoof` is a placement mechanism that leaves the
weights honest, and `CompositeAttack` had no `shape_update` method, so the boost was
silently swallowed by the base-class no-op. Every row recorded `payload=boost` and nothing
was boosted. The table showed all six rules tied at no damage, which looked like a finding.

**Second, the fix diverged.** Boosting the flat vector scales the whole `state_dict`,
including BatchNorm's `running_var` — 1,924 of `dnn_flat`'s 578,894 coordinates. Scaling a
variance drives it negative, the forward pass takes its square root, and the model emits
NaN. Victim accuracy read **0.0000** and FedAvg appeared to lose *everything*. A boost of
as little as **1.2×** did it, which is what gave it away: model replacement does not
destroy a network at 1.2×.

That second number would have been the most impressive result in this document and it was
an artefact — and worse, a **trivially detectable** one, since divergence to NaN is the
cheapest thing a server can check for. It is the same trap section 5 already flags for the
sign-flip detection rate. `WeightBoost` now amplifies **learnable parameters only**, which
is what model replacement actually specifies, and the boost behaves like a graded poison:
victim accuracy 0.9080 / 0.8800 / 0.7150 at 2× / 5× / 10× with finite logits throughout.

## 9. What this does not establish

- **There is no deployed defence here, and therefore no operating point.** This is an
  attack study. The fingerprint numbers describe the attack's *signature*, not a
  countermeasure anyone should ship.
- **Fingerprinting was the intended contribution, and it does not work.** 0.250 against a
  0.343 false-alarm rate.
- **Three seeds, not five.** The archived notebook's "6" is seeds × datasets, and the live
  re-run is 3 seeds. Part A's five-seed standard is not met here.
- **The live re-run has only two architectures.** Both dense. Whether the shape check
  stays all-or-nothing when two architectures happen to share a parameter count — which is
  easy to arrange deliberately — is **untested and is the obvious next experiment**.
- **The victim-impact numbers sit on a Dirichlet partition** the project has moved away
  from. Relative degradations transfer; absolute accuracies should not be quoted.
- **The two evidence bodies have not been unified.** Sections 4 and 8 are live Torch runs;
  sections 2, 3, 5, 6 are the archived corpus. They agree on the tier structure, but no
  single run produces both.
- **`n_params` identifying the architecture at 1.000 is a fact about this pool.** Five
  architectures with five distinct sizes. It is not a law.
- **Section 8 tests one payload at one scale.** A 10× weight boost is the classic model
  replacement attack, and the five robust rules contain it. Whether they contain a payload
  *designed* to survive coordinate-wise filtering — a small, many-round, within-variance
  perturbation — is **untested**, and I would not claim they do.

## 10. Three things I would like your view on

**First**, is the "two channels, opposite failure modes" framing the right spine for the
report? I think it is the strongest thing we have, because it turns two separate attack
studies into one argument about *what the server is trusting*. But it means the report
leads with a structural claim rather than with a result.

**Second**, how much should the archived corpus be leaned on? It is reproducible — the
verifier passes — and it covers ground the live re-run does not. But it predates the
partition change, and a reader who notices the `old_code/` path will ask. My inclination
is to keep it, clearly labelled, and say exactly what it can and cannot support.

**Third**, is the equal-parameter-count experiment worth running before the deadline? It
is the one result that would change the section 4 conclusion, because it is the only
plausible way the naive tier stops being free to catch. It is cheap — one new architecture
in the pool — but it competes with the report section that is still unwritten.
